# 이 저장소를 유지할 이유와 한계

Jev Decision Kit의 현재 역할은 공식 TypeSafe SDK를 대체하는 것이 아니라, 여러 앱이 동일한 응답 검사와 실패·관측 형식을 공유하는 작은 어댑터입니다. CLI와 스킬은 그 어댑터를 시험하는 보조 도구입니다. 단순히 Jev를 호출하려는 프로젝트라면 공식 SDK를 직접 사용하는 편이 더 간단합니다.

## 공식 도구와 비교

2026-09-27에 공식 SDK 소스, 공식 스킬과 Kev 문서를 확인했습니다. 아래는 현재 구현 기준이며, 개발 계획을 제공 기능으로 포함하지 않습니다.

| 도구 | 제공하는 역할 | 이 저장소와의 관계 |
| --- | --- | --- |
| TypeSafe API·공식 SDK | Jev의 판단 실행, 질문에서 응답 타입 추론, 시간 제한·취소·재시도·오류 처리, 요청 ID·사용량 | 이 저장소도 공식 SDK를 사용합니다. 이 기능들은 자체 차별점이 아닙니다. |
| TypeSafe 공식 스킬 | 작업에서 판단 지점을 찾고, 최신 문서에 따라 질문과 워크플로를 설계·구현 | 에이전트가 Jev를 활용하게 하는 것 자체는 이 저장소만의 기능이 아닙니다. |
| Kev | Jev와 호환되는 자체 모델, 학습·확률 보정·평가·자체 서버 운영, 관련 에이전트 스킬 | 모델을 만드는 다른 계층의 도구입니다. 이 저장소에는 모델 학습·보정·서빙 기능이 없습니다. |
| Jev Decision Kit | 질문과 응답의 대응 검사, 공통 성공·실패 결과와 정의 버전 메타데이터, 기본 사례 평가·집계, 시험용 CLI·스킬 설치 | 앱마다 반복할 검사와 결과 형식을 공유합니다. 앱의 판단 정책과 운영 연동은 별도 구현입니다. |

근거: [공식 SDK 타입](https://github.com/typesafe-ai/typesafe-sdk-js/blob/66880ccded6cb642dc1809620c2b108c33730214/src/types.ts), [공식 SDK 클라이언트](https://github.com/typesafe-ai/typesafe-sdk-js/blob/66880ccded6cb642dc1809620c2b108c33730214/src/client.ts), [공식 스킬](https://github.com/typesafe-ai/skills/blob/65a39f393687675ce170e6094757de20370365b9/skills/typesafe-ai/SKILL.md), [Kev README](https://github.com/jaredpalmer/kev/blob/5920c5fe4ca8e0970ed4209ac2c9b8e18bea5109/README.md).

Kev는 Jev를 단순히 감싼 패키지가 아닙니다. 자체 모델을 학습하고 실행하며 TypeSafe와 호환되는 API를 제공합니다. 이 저장소의 `baseURL` 설정만으로 Kev 호환성을 검증했다고 볼 수 없으며, 현재 Kev 서버를 대상으로 한 통합 테스트는 없습니다.

## 실제로 추가하는 기능

**질문에 맞는 응답인지 실행 중에 검사합니다.** 현재 확인한 공식 SDK는 성공 응답을 파싱한 뒤 타입으로 반환합니다. 이 저장소의 [`validateAnswers`](../packages/decisions/src/validation.ts)는 질문 ID·응답 종류·허용 선택지·확률 키와 범위·합계·선택 결과·점수의 일관성을 검사하고, 맞지 않으면 `invalid_response`를 반환합니다. 이것은 데이터 형식과 일관성 검사이며 업무상 정답 검증은 아닙니다.

**실패와 관측 메타데이터를 같은 형식으로 반환합니다.** [`createDecisionClient`](../packages/decisions/src/index.ts)는 `ok` 성공·실패 결과에 질문 정의 ID·버전, 모델, 요청 ID, 처리 시간과 확인 가능한 토큰 사용량을 붙입니다. 사용량이 없으면 0으로 간주하지 않고 `null`로 둡니다. 기본 재시도 0회, 제한 시간 1.2초, 요청 크기 제한도 공유하지만, 재시도와 시간 제한 자체는 공식 SDK로도 설정할 수 있습니다. 저장소가 관측 데이터를 자동으로 저장하는 것은 아닙니다.

**평가 결과를 같은 형식으로 집계합니다.** [`evaluateCases`·`summarize`](../packages/eval/index.mjs)는 호출자가 제공한 실행·정답 판정 함수로 사례를 평가하거나 기존 기록을 집계합니다. 적용·보류·실패·정답 수, 사례 그룹, 처리 시간과 알려진 사용량을 구분합니다. CLI의 `eval`은 이미 생성한 기록을 집계합니다. 정답 데이터 수집, 확률 보정, 임계값 탐색과 자동 운영 적용은 제공하지 않습니다.

CLI는 질문·선택지를 명령으로 시험하고, 스킬은 에이전트가 그 명령을 호출하도록 안내합니다. `connect`는 패키지와 도구의 설치를 줄입니다. 설치 편의는 보조 가치이며 앱 연동이나 판단 품질을 대신하지 않습니다. [설치가 바꾸는 파일과 남는 구현](integration.md).

## 유지할 가치가 생기는 조건

여러 앱에서 같은 응답 검증과 실패·관측 계약을 유지해야 한다면, 수정과 검증을 한 곳에서 공유할 수 있습니다. 반대로 한 앱에서 몇 개 질문만 호출하고 공식 SDK의 결과를 바로 사용한다면 추가 패키지·API·릴리스를 관리할 이유가 작습니다.

현재는 별도 범용 플랫폼으로서 강한 차별성이 있다고 평가하기 어렵습니다. 정확도·비용·속도 개선이나 유지보수 비용 감소를 실제 운영 데이터로 입증하지 않았습니다. 자체 질문 타입과 검증 규칙을 공식 API 변경에 맞추고, 패키지 버전·배포 파일·도구를 관리하는 비용도 생깁니다. 예를 들어 현재 검증기는 `choice` 선택지를 2개 이상 요구하므로 공식 API 전체와 동일한 기능 범위를 보장하지 않습니다.

유지한다면 응답 검사와 공통 결과·관측 계약에 범위를 집중하는 것이 타당합니다. 이 계약이 여러 앱에서 실제로 쓰이지 않거나 공식 SDK가 충분히 제공하게 되면, 공식 SDK 직접 사용으로 정리하거나 필요한 검증 유틸리티만 남기는 편이 낫습니다. 새 CLI나 설치 기능을 더 만드는 것으로 존재 이유를 대신하지 않습니다.
